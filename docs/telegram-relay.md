# اتصال تلگرام از سرور ایران

`api.telegram.org` از ایران در دسترس نیست. پس درخواست‌های تلگرام باید از
سرور خارج شما رد شوند.

```
سرور ایران (پنل)  ──HTTPS──►  سرور خارج (واسط)  ──►  api.telegram.org
```

پنل فقط یک متغیر می‌خواهد: `TELEGRAM_API_BASE`. بقیه‌اش تنظیم انجین‌ایکس
روی سرور خارج است.

---

## سه چیز که پیش از شروع باید بدانید

**۱. توکن ربات داخل خودِ آدرس است.** تلگرام مسیرش این شکلی است:

```
https://api.telegram.org/bot<توکن>/sendMessage
```

یعنی هرجا آن آدرس ثبت شود، توکن هم ثبت شده. دو نتیجه مستقیم دارد:

- **لاگ انجین‌ایکس روی واسط باید خاموش باشد.** با لاگ پیش‌فرض، توکن
  ربات شما داخل یک فایل متنی روی سرور خارج می‌نشیند.
- **مسیر ایران تا خارج باید رمزنگاری‌شده باشد.** با HTTP ساده، توکن در
  مسیر قابل خواندن است.

**۲. واسط باید فقط برای سرور شما باز باشد.** بدون محدودیت آی‌پی، یک
پروکسی باز به تلگرام ساخته‌اید که هر کسی می‌تواند با ربات خودش از آن
استفاده کند — و ترافیکش به نام سرور شما ثبت می‌شود.

**۳. توکن را در خط فرمان تایپ نکنید.** در تاریخچه شل می‌ماند. پایین‌تر
نشان داده شده چطور از `.env` بخوانیدش.

---

## قدم ۱ — ساخت ربات

در تلگرام به [@BotFather](https://t.me/BotFather) پیام بدهید:

1. `/newbot`
2. یک نام نمایشی بدهید — مثلاً `پاسارگاد میزبان`
3. یک نام کاربری بدهید که به `bot` ختم شود — مثلاً `pasargad_host_bot`

توکنی می‌دهد به شکل `1234567890:AAF...`. **این توکن رمز ربات شماست**؛
هرکس داشته باشد می‌تواند به‌جای شما پیام بفرستد و پیام‌های ربات را
بخواند.

بعد، برای اینکه دکمه Start در لینک اتصال درست کار کند:

```
/setjoingroups  →  ربات را انتخاب کنید  →  Disable
```

ربات فقط با تک‌نفره کار دارد؛ بستن گروه‌ها یعنی کسی نمی‌تواند آن را در
گروهی بیندازد و پیام‌های نامربوط بفرستد.

---

## قدم ۲ — واسط روی سرور خارج

دو راه دارید. اولی رایج‌تر است، دومی اگر دامنه ندارید.

### راه الف — زیردامنه با گواهی (پیشنهادی)

یک زیردامنه به آی‌پی سرور خارج اشاره بدهید، مثلاً `tg.example.com`.

روی **سرور خارج**:

```bash
apt update && apt install -y nginx certbot python3-certbot-nginx
certbot --nginx -d tg.example.com
```

بعد فایل `/etc/nginx/sites-available/telegram-relay` را بسازید:

```nginx
server {
  listen 443 ssl;
  server_name tg.example.com;

  ssl_certificate     /etc/letsencrypt/live/tg.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/tg.example.com/privkey.pem;

  # توکن ربات داخل مسیر آدرس است. با لاگ پیش‌فرض، توکن در فایل لاگ
  # می‌نشیند و هرکس به سرور دسترسی خواندن داشته باشد آن را دارد.
  access_log off;

  # فقط از آی‌پی سرور ایران. بدون این، یک پروکسی باز به تلگرام
  # ساخته‌اید که هر کسی می‌تواند از آن استفاده کند.
  allow 203.0.113.10;   # ← آی‌پی سرور ایران خودتان
  deny all;

  location / {
    resolver 1.1.1.1 8.8.8.8 valid=300s;

    # نام میزبان در متغیر است تا انجین‌ایکس آی‌پی را فقط هنگام شروع حل
    # نکند. با متغیر، انتقال مسیر و کوئری خودکار نیست — پس
    # $request_uri صریح گذاشته شده.
    set $tg api.telegram.org;
    proxy_pass https://$tg$request_uri;

    proxy_ssl_server_name on;
    proxy_set_header Host api.telegram.org;
    proxy_http_version 1.1;

    proxy_connect_timeout 15s;
    proxy_read_timeout    60s;

    # فرستادن فایل و عکس از همین مسیر رد می‌شود
    client_max_body_size 20m;
  }
}
```

> **چرا `http2` اینجا نیست.** دستور مستقل `http2 on;` از انجین‌ایکس
> ۱٫۲۵٫۱ به بعد آمده. اوبونتو ۲۲٫۰۴ نسخه ۱٫۱۸ دارد و ۲۴٫۰۴ نسخه ۱٫۲۴،
> پس روی هر دو با `unknown directive "http2"` می‌شکند. شکل قدیمی‌اش
> (`listen 443 ssl http2;`) هم روی نسخه‌های تازه اخطار منسوخ‌شدن
> می‌دهد.
>
> برای این واسط اصلاً لازم نیست: چند درخواست کوچک ای‌پی‌آی است، نه
> صفحه‌ای با ده‌ها فایل. نبودنش روی هر نسخه‌ای کار می‌کند.

**دامنه در سه جای این فایل تکرار شده** — `server_name` و دو مسیر گواهی.
هر سه را با هم عوض کنید:

```bash
sed -i 's/tg\.example\.com/tg.YOURDOMAIN.com/g' /etc/nginx/sites-available/telegram-relay
```

فعالش کنید:

```bash
ln -s /etc/nginx/sites-available/telegram-relay /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
```

`nginx -t` را جدی بگیرید: انجین‌ایکس با پیکربندی نامعتبر اصلاً بالا
نمی‌آید.

اگر `nginx -t` خطای `unknown directive` داد، نسخه انجین‌ایکس را ببینید و
همان دستور را از فایل بردارید:

```bash
nginx -v
```

### اگر بعداً ۴۰۴ گرفتید

`404` که **متن انجین‌ایکس** دارد (نه جیسون تلگرام) یعنی درخواست به سرور
خارج رسیده ولی به بلوک واسط نخورده و بلوک دیگری جوابش داده.

دو علت، هر دو رایج:

```bash
nginx -T 2>/dev/null | grep -n "server_name\|ssl_certificate \|listen "
```

> `nginx -T` پیکربندی **مؤثر** را چاپ می‌کند. با `grep -r` روی
> `sites-enabled/` جواب نگیرید: آن پوشه پر از سیم‌لینک است و `grep -r`
> از سیم‌لینک‌های داخل پوشه رد می‌شود — خروجی خالی می‌دهد و شما فکر
> می‌کنید پیکربندی خالی است.

۱. **`server_name` هنوز `tg.example.com` است.** همان `sed` بالا را
   بزنید.

۲. **بلوک دیگری همان نام را ادعا می‌کند.** `certbot --nginx` هنگام صدور
   گواهی، نام دامنه را به بلوکی که آن موقع وجود داشته اضافه می‌کند —
   معمولاً `default`. حالا دو بلوک یک نام دارند و اولی که بارگذاری
   می‌شود برنده است.

```bash
nginx -T 2>/dev/null | grep -c "server_name tg.YOURDOMAIN.com"
```

اگر بیشتر از ۱ بود، دو بلوک آن نام را دارند. کدام فایل‌ها:

```bash
grep -Rln "tg.YOURDOMAIN.com" /etc/nginx/sites-available/ /etc/nginx/conf.d/
```

معمولاً آن یکی `sites-available/default` است: `certbot --nginx` یک بلوک
HTTPS با نام دامنه شما داخلش ساخته که ریشه‌اش `/var/www/html` است.

**`default` را حذف نکنید** — بلوک پیش‌فرض پورت ۸۰ و ریدایرکت
`http→https` هم داخلش هستند. فقط ادعای نام را از همان یک بلوک بردارید:

```bash
cp /etc/nginx/sites-available/default /root/default.bak
sed -i 's/^\(\s*\)server_name tg\.YOURDOMAIN\.com; # managed by Certbot/\1server_name _;/' /etc/nginx/sites-available/default
nginx -t && systemctl reload nginx
```

الگو عمداً `# managed by Certbot` را هم شرط کرده تا فقط همان یک خط عوض
شود؛ خط ریدایرکت پورت ۸۰ که همان نام را دارد ولی این توضیح را ندارد،
دست‌نخورده می‌ماند.

پس از این، آن بلوک روی ۴۴۳ «هر نام دیگری» می‌شود. تطبیق نام دقیق بر
catch-all اولویت دارد، پس درخواست‌های دامنه شما به واسط می‌روند.

بررسی:

```bash
nginx -T 2>/dev/null | grep -c "server_name tg.YOURDOMAIN.com;"
```

باید `2` بدهد — یکی ریدایرکت پورت ۸۰، یکی واسط روی ۴۴۳.

### راه ب — تونل وایرگارد (بدون دامنه)

اگر دامنه ندارید، یک تونل وایرگارد بین دو سرور بزنید و انجین‌ایکس را
روی آی‌پی تونل و HTTP ساده بگذارید. رمزنگاری را خود وایرگارد انجام
می‌دهد، پس گواهی لازم نیست.

روی سرور خارج، `listen` و `server_name` را عوض کنید:

```nginx
server {
  listen 10.20.0.1:8081;   # ← آی‌پی تونل سرور خارج
  server_name _;

  access_log off;

  location / {
    resolver 1.1.1.1 8.8.8.8 valid=300s;
    set $tg api.telegram.org;
    proxy_pass https://$tg$request_uri;
    proxy_ssl_server_name on;
    proxy_set_header Host api.telegram.org;
    proxy_http_version 1.1;
    proxy_read_timeout 60s;
    client_max_body_size 20m;
  }
}
```

`allow/deny` لازم نیست چون فقط روی آی‌پی تونل گوش می‌دهد. **حتماً روی
آی‌پی تونل، نه `0.0.0.0`** — وگرنه همان پروکسی باز است.

## قدم ۳ — آزمودن واسط از سرور ایران

روی **سرور ایران**، در پوشه پنل:

```bash
cd /root/pasargad-monitor
TG=$(grep '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-)
curl -s "https://tg.example.com/bot$TG/getMe"
```

توکن از `.env` خوانده می‌شود، نه تایپ — پس در تاریخچه شل نمی‌ماند.

پاسخ درست:

```json
{"ok":true,"result":{"id":123,"is_bot":true,"username":"pasargad_host_bot",...}}
```

اگر `ok: false` یا خطای شبکه گرفتید، جلوتر نروید — بقیه مراحل بدون این
کار نمی‌کنند.

| نشانه | علت |
|---|---|
| `403 Forbidden` | آی‌پی سرور ایران در `allow` نیست |
| `502` یا تایم‌اوت | سرور خارج به تلگرام نمی‌رسد، یا `resolver` نیست |
| `{"ok":false,...401}` | توکن غلط است |
| اتصال برقرار نمی‌شود | دامنه به آی‌پی درست اشاره نمی‌کند یا فایروال بسته است |

## قدم ۴ — تنظیم پنل

روی سرور ایران، در `.env`:

```bash
TELEGRAM_BOT_TOKEN=1234567890:AAF...
TELEGRAM_API_BASE=https://tg.example.com
```

اگر راه ب را رفتید: `TELEGRAM_API_BASE=http://10.20.0.1:8081`

**بدون اسلش انتهایی.** پنل خودش اضافه‌اش می‌کند.

بعد سرویس‌ها را دوباره بالا بیاورید. `TELEGRAM_API_BASE` هم به `web`
می‌رود هم به `worker`، پس هر دو لازم‌اند:

```bash
docker compose up -d web worker
```

`.env` هرگز در گیت نرود.

## قدم ۵ — بررسی اینکه ورکر ربات را شناخت

ورکر خودش با `getMe` نام ربات را می‌گیرد و در تنظیمات می‌نویسد. تا وقتی
این نام خالی است، هیچ مشتری‌ای نمی‌تواند تلگرامش را وصل کند.

```bash
docker compose logs worker --tail 50 | grep -i تلگرام
```

باید ببینید:

```
نام کاربری ربات تلگرام ثبت شد: pasargad_host_bot
```

در پنل هم: **تنظیمات ← تلگرام مشتری** — کادر «ربات» باید نام ربات را
نشان بدهد. اگر خالی است و هشدار زرد می‌بینید، یعنی هنوز وصل نشده و
قدم ۳ را دوباره بررسی کنید.

### اگر خطای Conflict دیدید

```
تلگرام: وب‌هوک تنظیم شده و خواندن پیام‌ها ممکن نیست
```

یعنی روی این ربات قبلاً وب‌هوک تنظیم شده. برداشتنش:

```bash
curl -s "https://tg.example.com/bot$TG/deleteWebhook"
```

اتصال مشتری با خواندن پیام‌ها کار می‌کند، نه وب‌هوک — دلیلش در
[docs/customer-telegram.md](customer-telegram.md) نوشته شده.

## قدم ۶ — هشدارهای خودتان

این جدا از تلگرام مشتری است: هشدار قطعی سرور و آستانه‌ها به گفتگوی خود
شما می‌رود.

۱. در تلگرام ربات خودتان را باز کنید و `/start` بزنید.

۲. روی سرور ایران:

```bash
docker compose logs worker --tail 20 | grep گفتگوی
```

خطی می‌بینید مثل:

```
پیام تلگرام از گفتگوی 987654321
```

آن عدد شناسه گفتگوی شماست.

۳. در پنل: **تنظیمات ← هشدارها** — تلگرام را فعال کنید و همان عدد را در
«شناسه گفتگو» بگذارید. چند نفر را با کاما جدا کنید.

۴. آزمایش: یک سرور را موقتاً خاموش کنید، یا صبر کنید تا اولین هشدار
واقعی بیاید.

> ربات فقط به کسی پیام می‌دهد که خودش اول به ربات پیام داده باشد. اگر
> `/start` نزنید، تلگرام ارسال را با `chat not found` رد می‌کند.

## قدم ۷ — آزمودن اتصال مشتری

۱. در پنل: **تنظیمات ← تلگرام مشتری** فعال باشد.

۲. با حساب یک مشتری وارد پرتال شوید: **پروفایل ← اتصال تلگرام**.

۳. روی «باز کردن تلگرام و اتصال» بزنید و در تلگرام **Start** را لمس
   کنید.

۴. تا ده ثانیه، همان صفحه پروفایل خودش به‌روز می‌شود و «متصل» نشان
   می‌دهد.

اگر نشد:

```bash
docker compose logs worker --tail 40 | grep -i تلگرام
```

| نشانه در لاگ | یعنی |
|---|---|
| هیچ خطی نیست | ورکر پیام را نمی‌خواند — قدم ۳ و ۵ را بررسی کنید |
| `Conflict` | وب‌هوک تنظیم است؛ `deleteWebhook` بزنید |
| «این کد معتبر نیست یا منقضی شده» | کد پنج دقیقه اعتبار دارد؛ کد تازه بگیرید |

## نگهداری

**تمدید گواهی.** `certbot` خودش تمدید می‌کند، ولی یک بار بررسی کنید:

```bash
certbot renew --dry-run
```

اگر گواهی منقضی شود، همه پیام‌های تلگرام بی‌صدا قطع می‌شوند — نه پنل
خطا می‌دهد نه مشتری متوجه می‌شود. فقط در لاگ ورکر پیداست.

**اگر آی‌پی سرور ایران عوض شد**، `allow` روی واسط را هم عوض کنید، وگرنه
همه چیز `403` می‌گیرد.

**پایش سلامت واسط.** ماهی یک بار از سرور ایران:

```bash
TG=$(grep '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-)
curl -s "https://tg.example.com/bot$TG/getMe" | head -c 80
```

---

## اگر روزی توکن لو رفت

در BotFather: `/revoke` → ربات را انتخاب کنید. توکن تازه می‌گیرد.

توکن تازه را در `.env` بگذارید و `docker compose up -d web worker`.
**اتصال‌های مشتری‌ها دست‌نخورده می‌مانند** — شناسه گفتگو در دیتابیس است،
نه وابسته به توکن.
