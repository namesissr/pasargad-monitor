# سوییچ‌ها — NX-API، SNMP v2c و SNMP v3

پنل هر سوییچ را هر ۳۰ ثانیه می‌خواند، از یکی از سه راه:

| روش | برای | خاموش و روشن کردن پورت |
|---|---|---|
| **NX-API** | Cisco Nexus (سری ۳۰۰۰ و ۹۰۰۰، NX-OS 7 به بعد) | بله، با نقش کاربر سوییچ |
| **SNMP v2c** | هر برند | فقط اگر کامیونیتی نوشتنی جدا بدهید |
| **SNMP v3** | هر برند — امن‌ترین راه SNMP | فقط اگر «اجازه نوشتن» را روشن کنید. روی Cisco Nexus محدودیت سرعت و پشتیبان پیکربندی هم ([بخش ۱۳](#۱۳-محدودیت-سرعت-و-پشتیبان-پیکربندی-با-snmp-v3-cisco-nexus)) |

NX-API برای نکسوس کامل‌ترین است (توان نوری ماژول‌ها فقط از این راه خوانده می‌شود). SNMP برای بقیه سوییچ‌ها —
سیسکو IOS، میکروتیک، جونیپر، هوآوی، آریستا و… — یا نکسوسی که نمی‌خواهید NX-API رویش روشن شود. راه‌اندازی SNMP
در [بخش ۸](#۸-snmp-v2c-و-v3) است.

آنچه پنل نشان می‌دهد:

| بخش | چه چیزی |
|---|---|
| هر پورت | وضعیت لینک و shut، سرعت، حالت و ویلن، سرعت لحظه‌ای ورودی و خروجی، مصرف امروز و ماه، خطا و discard، توان نوری ماژول، تاریخچه قطع و وصل |
| همسایه‌ها | دستگاه آن طرف هر پورت از LLDP و CDP، MACهای پشت هر پورت با آی‌پی‌شان، و جست‌وجوی «این آی‌پی یا MAC روی کدام پورت است» |
| پیشنهاد اتصال | پنل از LLDP، جدول MAC/ARP یا توضیح پورت حدس می‌زند هر پورت مال کدام سرور است؛ با یک کلیک تأیید یا رد |
| خود سوییچ | پردازنده، حافظه، بار، دما، فن، منبع تغذیه، آپ‌تایم، مدل، سریال، نسخه NX-OS |
| نمودار | سرعت هر پورت و منابع سوییچ — ۱ ساعت تا ۳ ماه |
| کنترل | خاموش و روشن کردن پورت، ویرایش توضیح (description)، محدودیت سرعت پورت — فقط از حساب مدیر |
| پشتیبان پیکربندی | running-config روزانه و پس از هر فرمان پنل؛ تاریخچه نسخه‌ها، تفاوت هر نسخه با قبلی، رازها پوشیده |
| گزارش | حجم، اوج، صدک ۹۵، بهره‌وری، خطا و قطع هر پورت در ماه یا بازه دلخواه، با خروجی CSV؛ کارت سوییچ‌ها در داشبورد |
| هشدار | عدم دسترسی به سوییچ، مشکل فن/تغذیه/دما، پردازنده بالا، قطعی لینک، اشباع پورت، خطای پورت، قطع و وصل مکرر |
| سرور | پورت به سرور وصل می‌شود و مصرفش می‌تواند به‌جای عدد ایجنت مبنای سهمیه و حسابداری باشد |

ورکر مستقیم به آی‌پی مدیریت سوییچ (mgmt0) وصل می‌شود. پس **سرور پنل باید به شبکه مدیریت سوییچ دسترسی داشته باشد** — قدم ۲ همین را می‌سنجد (برای SNMP، بخش ۸).

## ۱. آماده‌سازی سوییچ

```
configure terminal
  feature nxapi
  ! پیش‌فرض HTTPS روی ۴۴۳ است؛ فقط اگر می‌خواهید عوض شود
  nxapi https port 443
end
show nxapi
```

### کاربر

برای **فقط پایش**، نقش فقط‌خواندنی کافی است:

```
configure terminal
  username panel password <گذرواژه-قوی> role network-operator
end
```

برای **shut / no shut** هم، کاربر باید اجازه پیکربندی اینترفیس داشته باشد. ساده‌ترین راه `role network-admin` است.
اگر دسترسی محدودتر می‌خواهید، یک نقش سفارشی بسازید — نحو دقیق قاعده‌ها بین نسخه‌های NX-OS کمی فرق دارد، پس
روی سوییچ خودتان امتحانش کنید:

```
configure terminal
  role name panel-ops
    rule 10 permit read
    rule 20 permit command configure terminal
    rule 30 permit command interface *
    rule 40 permit command shutdown
    rule 50 permit command no shutdown
    rule 60 permit command copy running-config startup-config
    ! توضیح پورت
    rule 70 permit command description *
    rule 80 permit command no description
    ! محدودیت سرعت
    rule 90 permit command policy-map *
    rule 100 permit command class *
    rule 110 permit command police *
    rule 120 permit command service-policy *
    rule 130 permit command no service-policy *
  username panel password <گذرواژه-قوی> role panel-ops
end
```

`permit read` برای پشتیبان پیکربندی (`show running-config`) کافی است، ولی NX-OS در آن هش گذرواژه‌ها را هم نشان
می‌دهد؛ پنل آن را فقط به حساب مدیر و پوشیده نشان می‌دهد (بخش ۱۱).

اگر کاربر اجازه نداشته باشد، پایش کار می‌کند و فقط فرمان shut با پیام «اجازه این فرمان را ندارد» شکست می‌خورد.

> هر فرمانی که پنل اجرا می‌کند با همین نام کاربری در accounting خود سوییچ (`show accounting log`) هم ثبت می‌شود.

**امنیت:** دسترسی به NX-API را با ACL فقط به آی‌پی سرور پنل محدود کنید.

## ۲. آیا سرور پنل به سوییچ می‌رسد؟

روی **سرور پنل** (همان‌جا که داکر اجرا می‌شود):

```bash
curl -sk -u panel:'گذرواژه' https://10.0.0.5/ins \
  -H 'content-type: application/json' \
  -d '{"ins_api":{"version":"1.0","type":"cli_show","chunk":"0","sid":"1","input":"show version","output_format":"json"}}' | head -c 400
```

| نتیجه | معنی |
|---|---|
| جیسون با `"code": "200"` | آماده است |
| بعد از چند ثانیه هیچ | سرور پنل به شبکه مدیریت سوییچ راه ندارد — مسیر، فایروال یا ACL |
| `Connection refused` | NX-API روشن نیست یا پورتش فرق دارد |
| `401` | نام کاربری یا گذرواژه |

اگر سرور پنل هیچ راهی به شبکه مدیریت ندارد (مثلا پنل در دیتاسنتر دیگری است)، این نسخه هنوز کار نمی‌کند؛ راه‌حلش
یک واسط کوچک داخل همان شبکه است که سوییچ را بخواند و به پنل بفرستد. صف فرمان‌ها از اول برای همین طراحی شده.

## ۴. پورت و سرور

روی هر پورت **جزئیات ← تنظیمات پورت در پنل**:

- **سرور متصل** — مصرف پورت در صفحه همان سرور هم دیده می‌شود. هشدار قطعی لینک پیش‌فرض روشن می‌شود.
- **مبنای ترافیک سرور** — از این لحظه، ترافیک سرور در سهمیه، حسابداری، گزارش، فاکتور و پرتال مشتری از سوییچ
  می‌آید نه از ایجنت. روزها و ساعت‌های گذشته دست نمی‌خورند.
- **محافظت‌شده** — از پنل خاموش نمی‌شود. آپلینک‌ها و پورت‌چنل هسته را محافظت‌شده کنید. `mgmt0` خودکار
  محافظت‌شده است و هرگز از پنل خاموش نمی‌شود.

### جهت‌ها

در صفحه سوییچ همه‌چیز از دید **سوییچ** است: «ورودی» یعنی وارد سوییچ شده، «خروجی» یعنی از سوییچ بیرون رفته.
برای پورتی که به سرور وصل است:

| سوییچ | سرور |
|---|---|
| خروجی (out) | دانلود (rx) |
| ورودی (in) | آپلود (tx) |

صفحه سرور همین را از دید سرور نشان می‌دهد.

### چرا سوییچ دقیق‌تر از ایجنت است

- نیازی به نصب چیزی روی سرور مشتری نیست — سرور بدون ایجنت هم مصرف دارد.
- شمارنده سوییچ پایدار است: اگر ورکر ری‌استارت شود یا سوییچ مدتی در دسترس نباشد، حجم آن فاصله گم نمی‌شود و در
  اولین خواندن بعدی می‌آید. (در قطعی طولانی سوییچ، آن حجم یک‌جا در ساعت برگشت ثبت می‌شود.)
- آنچه دیتاسنتر فاکتور می‌کند هم معمولا از همین شمارنده‌هاست.

اگر هم پورت‌چنل و هم عضوهایش برای یک سرور «مبنای ترافیک» باشند، عضوها کنار می‌روند تا دو بار شمرده نشود.

## ۵. خاموش و روشن کردن پورت

**جزئیات پورت ← خاموش کردن**. فقط حساب `admin`؛ `operator` و `viewer` نمی‌توانند.

۱. دلیل نوشته می‌شود (در تاریخچه می‌ماند).
۲. اگر پورت به سرور وصل است، نام پورت باید تایپ شود — یک کلیک اشتباه نباید سرویس مشتری را قطع کند.
۳. ورکر ظرف چند ثانیه فرمان را اجرا می‌کند و **بعد وضعیت واقعی پورت را از سوییچ می‌خواند**. «فرمان بدون خطا رفت»
   با «پورت واقعا خاموش شد» یکی نیست.
۴. نتیجه و تاریخچه کامل پایین صفحه سوییچ است: چه کسی، کی، کدام پورت، چرا، و چه شد.

**ماندگار پس از ریبوت:** بدون تیک «copy running-config startup-config»، تغییر با ریبوت سوییچ برمی‌گردد. با تیک،
کل running-config ذخیره می‌شود — **هر تغییر ذخیره‌نشده دیگری روی سوییچ هم با آن**.

سروری که همه پورت‌هایش از پنل shut شده‌اند، هشدار «سرور قطع شد» نمی‌دهد؛ قطعی عمدی است.

## ۶. هشدارها

| رویداد | کی |
|---|---|
| عدم دسترسی به سوییچ | دو خواندن پشت‌سرهم شکست بخورد |
| سخت‌افزار سوییچ | فن یا منبع تغذیه خراب/بی‌برق، یا دما بالای حد بحرانی خود سوییچ — هر ۵ دقیقه بررسی |
| پردازنده سوییچ بالا | میانگین ۵ دقیقه بالای آستانه (پیش‌فرض ۹۰٪) |
| قطعی پورت | فقط پورت‌هایی که «هشدار قطعی لینک» دارند، و بیش از یک دقیقه قطع بمانند |
| اشباع پورت | فقط پورت‌هایی که «هشدار اشباع» دارند: میانگین ۵ دقیقه بزرگ‌ترِ ورودی و خروجی بالای آستانه ظرفیت (پیش‌فرض ۹۰٪). برگشت زیر ۹۰٪ آستانه |
| خطای پورت | مجموع خطای ورودی، خروجی و CRC در ۱۵ دقیقه بالای آستانه (پیش‌فرض ۱۰۰). برگشت وقتی نیم ساعت تقریبا بی‌خطا. نشانه کابل یا ماژول خراب |
| قطع و وصل مکرر | چند بار قطع و وصل در ۱۵ دقیقه (پیش‌فرض ۵). برگشت وقتی ۱۵ دقیقه آرام |

«هشدار اشباع» پیش‌فرض برای پورت‌های محافظت‌شده (آپلینک‌ها) روشن است: اشباع آپلینک یعنی همه کند شده‌اند. پورت سروری
که با تمام ظرفیتش کار می‌کند معمولا مشکل نیست، پس برای آن خاموش است. هشدار خطا و قطع و وصل فقط برای پورت‌هایی است
که «زیر نظر»ند — وصل به سرور، محافظت‌شده، یا با یکی از دو هشدار — تا چهل پورت خالی با کابل شل پیامک نفرستند.
خاموش و روشن کردن عمدی از پنل قطع و وصل شمرده نمی‌شود.

اسلات خالی فن یا تغذیه مشکل حساب نمی‌شود؛ منبع تغذیه‌ای که هست ولی برق ندارد، مشکل است.
فاصله خواندن و همه آستانه‌ها در **تنظیمات ← پایش**؛ صفر هر آستانه آن هشدار را خاموش می‌کند.

## ۷. چه چیزی هر چند وقت خوانده می‌شود

| فرمان | فاصله |
|---|---|
| `show interface`، `show interface status`، `show system resources` | هر خواندن (پیش‌فرض ۳۰ ثانیه) |
| `show version` | ۵ دقیقه |
| `show environment temperature/fan/power` | ۵ دقیقه |
| `show interface transceiver details` | ۱۰ دقیقه |
| `show mac address-table`، `show ip arp vrf all`، `show lldp neighbors detail`، `show cdp neighbors detail` | ۵ دقیقه |
| `show running-config` | هر `switch_backup_hours` ساعت (پیش‌فرض ۲۴) و پس از هر فرمان موفق پنل |

همه فقط‌خواندنی‌اند. فرمان‌های پیکربندی فقط وقتی مدیر از پنل درخواست کند اجرا می‌شوند:
`interface X` + `shutdown`/`no shutdown`/`description …`/`service-policy …`، `policy-map type qos PANEL-RL-…`،
و در صورت انتخاب `copy running-config startup-config`.

نمونه خام هر پورت مثل سرورها `raw_retention_days` روز نگه داشته می‌شود؛ تجمیع پنج‌دقیقه‌ای (برای صدک ۹۵)
`switch_5min_days` روز (پیش‌فرض ۷۰)؛ تجمیع روزانه پورت هرگز پاک نمی‌شود. تاریخچه قطع و وصل ۹۰ روز، جدول ARP ۷ روز،
و از هر سوییچ ۲۰۰ نسخه آخر پیکربندی می‌ماند.

## ۸. SNMP v2c و v3

### روی سوییچ

**سیسکو (IOS و NX-OS):**

```
! v3، فقط پایش — پیشنهادی
snmp-server group PANEL v3 priv
snmp-server user panel PANEL v3 auth sha <گذرواژه-احراز> priv aes 128 <گذرواژه-رمز>

! v3 با اجازه shut/no shut: گروه باید write-view داشته باشد
snmp-server view ALL iso included
snmp-server group PANELRW v3 priv read ALL write ALL
snmp-server user panelrw PANELRW v3 auth sha <گذرواژه-احراز> priv aes 128 <گذرواژه-رمز>

! v2c
snmp-server community <کامیونیتی-خواندنی> RO <ACL>
snmp-server community <کامیونیتی-نوشتنی> RW <ACL>      ! فقط اگر shut از پنل لازم است
```

روی NX-OS نحو کاربر کمی فرق دارد (`snmp-server user panel network-operator auth sha … priv aes-128 …`، و برای
نوشتن نقش `network-admin`). با `show snmp user` بررسی کنید.

**میکروتیک (RouterOS 7):**

```
/snmp set enabled=yes
/snmp community add name=panel security=private authentication-protocol=SHA1 authentication-password=<…> \
    encryption-protocol=AES encryption-password=<…> addresses=<آی‌پی-سرور-پنل>/32 read-access=yes write-access=no
```

**هر سوییچی:** دسترسی SNMP را با ACL فقط به آی‌پی سرور پنل محدود کنید.

### در پنل

**سوییچ‌ها ← افزودن سوییچ ← SNMP v2c یا SNMP v3**، آی‌پی سوییچ و پورت UDP (پیش‌فرض ۱۶۱).

- **v2c:** کامیونیتی خواندنی. کامیونیتی نوشتنی اختیاری است؛ خالی یعنی سوییچ فقط پایش می‌شود.
- **v3:** نام کاربر، نوع و گذرواژه احراز هویت (SHA تا SHA-512، یا MD5 قدیمی)، نوع و گذرواژه رمزنگاری
  (AES-128، AES-256، یا DES قدیمی). گذرواژه‌ها دست‌کم ۸ نویسه. AES-256 دو گونه ناهمسان دارد: «سیسکو» برای
  سیسکو، «بقیه برندها» برای بقیه — اگر یکی کار نکرد دیگری را امتحان کنید.
- **اجازه نوشتن (v3):** فقط وقتی روشن کنید که کاربر روی سوییچ write-view دارد.

رازها (کامیونیتی و گذرواژه‌ها) هرگز به پنل برنمی‌گردند. با تغییر آی‌پی، پورت، نسخه یا کاربر باید دوباره وارد شوند
— وگرنه کسی که فقط آدرس را به سرور خودش تغییر می‌داد، رازها را از ورکر تحویل می‌گرفت.

### آیا سرور پنل به سوییچ می‌رسد؟

```bash
# v2c
docker compose exec worker node -e "
const s=require('net-snmp').createSession('10.0.0.5','<کامیونیتی>',{version:1});
s.get(['1.3.6.1.2.1.1.5.0'],(e,v)=>{console.log(e?e.message:String(v[0].value));s.close()})"
```

جواب نام سوییچ است. «Request timed out» یعنی کامیونیتی اشتباه است، یا SNMP روشن نیست، یا UDP 161 بسته است —
سوییچ‌ها به کامیونیتی اشتباه معمولا هیچ جوابی نمی‌دهند، پس این سه از هم جدا نمی‌شوند.

### چه چیزی از کجا خوانده می‌شود

| بخش | MIB |
|---|---|
| پورت‌ها، وضعیت، سرعت، شمارنده‌ها | IF-MIB (همه برندها). شمارنده ۶۴ بیتی اگر باشد، وگرنه ۳۲ بیتی با تشخیص سرریز |
| پورت‌چنل | IEEE8023-LAG-MIB |
| ویلن | سیسکو: CISCO-VLAN-MEMBERSHIP و VTP؛ بقیه: Q-BRIDGE-MIB |
| پردازنده و حافظه | سیسکو: CISCO-PROCESS-MIB یا CISCO-MEMORY-POOL-MIB؛ بقیه: HOST-RESOURCES-MIB |
| دما، فن، تغذیه | سیسکو: CISCO-ENVMON-MIB، یا در نکسوس CISCO-ENTITY-FRU-CONTROL و CISCO-ENTITY-SENSOR؛ بقیه: ENTITY-SENSOR-MIB؛ میکروتیک: دمای برد |
| مدل، سریال | ENTITY-MIB |
| shut / no shut | ifAdminStatus |
| توضیح پورت | ifAlias (حداکثر ۶۴ نویسه) |
| همسایه‌ها | LLDP-MIB؛ سیسکو: CISCO-CDP-MIB هم |
| MAC پشت هر پورت | Q-BRIDGE-MIB، وگرنه BRIDGE-MIB |
| ARP | IP-MIB (ipNetToMediaTable) |
| ذخیره در startup-config | CISCO-CONFIG-COPY-MIB — فقط سیسکو |
| محدودیت سرعت، پشتیبان پیکربندی | CISCO-CONFIG-COPY-MIB با انتقال فایل (SFTP/TFTP) — فقط سیسکو؛ محدودیت فقط نکسوس ([بخش ۱۳](#۱۳-محدودیت-سرعت-و-پشتیبان-پیکربندی-با-snmp-v3-cisco-nexus)) |

هر MIB که سوییچ نداشته باشد خطا نیست؛ آن بخش در پنل خالی می‌ماند. توان نوری ماژول‌ها با SNMP خوانده نمی‌شود.

سیسکو IOS جدول MAC را با SNMP فقط برای ویلن پیش‌فرض می‌دهد (برای بقیه ویلن‌ها کامیونیتی `community@vlan` لازم
است)؛ روی این سوییچ‌ها پیشنهاد اتصال بیشتر به LLDP تکیه می‌کند.

### ایمنی shut با SNMP

SNMP پورت را با شماره (ifIndex) می‌شناسد نه با نام، و بعضی سوییچ‌ها پس از ریبوت شماره‌ها را عوض می‌کنند. پیش از
هر SET، ورکر نام همان شماره را دوباره از سوییچ می‌پرسد؛ اگر با نام پورت نخواند، فرمان اجرا **نمی‌شود** و پیام
می‌دهد. پس از خواندن بعدی شماره درست شده و می‌شود دوباره امتحان کرد.

روی سوییچ غیرسیسکو تیک «ماندگار پس از ریبوت» غیرفعال است؛ ذخیره پیکربندی را روی خود سوییچ انجام دهید.

## ۹. همسایه‌ها، MAC و پیشنهاد اتصال

هر ۵ دقیقه، از هر سوییچ همسایه‌های LLDP/CDP، جدول MAC و جدول ARP خوانده می‌شود. در صفحه سوییچ، سربرگ
**همسایه‌ها و MAC**:

- برای هر پورت، دستگاه آن طرف (نام، پورتش، آی‌پی مدیریت) و تعداد MAC.
- **این آی‌پی یا MAC کجاست؟** — آی‌پی یا MAC (کامل یا چهار رقم آخر، با هر قالبی) را در همه سوییچ‌ها پیدا می‌کند.
  یک MAC روی چند پورت دیده می‌شود: پورتی که دستگاه به آن وصل است و همه آپلینک‌های مسیر. پورت با کمترین MAC اول
  می‌آید و «پورت لبه» علامت می‌خورد.

جدول ARP معمولا روی سوییچ لایه سه یا روتر است، نه سوییچ دسترسی. پنل ARP همه سوییچ‌هایش را با هم می‌بیند: سوییچ
دسترسی MAC را می‌گوید و سوییچ هسته آی‌پی را.

### پیشنهاد اتصال

با صدها پورت، اینکه کدام پورت مال کدام سرور است معمولا فقط در ذهن کسی است که کابل را زده. پنل سه نشانه را می‌سنجد:

| نشانه | اعتبار |
|---|---|
| همسایه LLDP خودش را با نام همان سرور معرفی می‌کند | قوی |
| MAC روی پورت، در جدول ARP به آی‌پی‌ای می‌رسد که در پنل مال سرور است (آی‌پی اصلی یا هر آی‌پی تخصیص‌یافته) | قوی |
| توضیح پورت نام یا آی‌پی سرور را دارد | ضعیف — فقط وقتی نشانه قوی نیست |

پیشنهاد فقط وقتی داده می‌شود که دقیقا **یک** سرور بماند. پورت محافظت‌شده، عضو پورت‌چنل، و پورتی که شبیه آپلینک
است (بیش از ۸ MAC، یا همسایه‌ای که سوییچ/روتر است) پیشنهاد MAC و توضیح نمی‌گیرد؛ نود مجازی‌سازی با ده‌ها MAC
ماشین مجازی هم با نام LLDP خودش پیدا می‌شود.

پیشنهادها در سربرگ «پورت‌ها» دیده می‌شوند. **تأیید** پورت را به سرور وصل و هشدار قطعی را روشن می‌کند؛ «مبنای
ترافیک» دست نمی‌خورد. **درست نیست** همان پیشنهاد را برای همیشه کنار می‌گذارد.

برای دقیق‌ترین پیشنهاد، روی سرورهای لینوکسی `lldpd` نصب کنید (`apt install lldpd`) — سرور خودش را با نام میزبانش
به سوییچ معرفی می‌کند. روی سوییچ: `feature lldp`.

## ۱۰. توضیح پورت و محدودیت سرعت

در **جزئیات پورت ← فرمان روی سوییچ**. فقط حساب مدیر، و مثل shut: دلیل، تیک ماندگاری، و اجرا در صف ورکر با خواندن
دوباره وضعیت واقعی.

**توضیح (description):** روی خود سوییچ نوشته می‌شود. «;» و خط تازه پذیرفته نیست (جداکننده فرمان‌اند). خالی یعنی
پاک شود. با SNMP از `ifAlias` (حداکثر ۶۴ نویسه) و نیاز به اجازه نوشتن دارد.

**محدودیت سرعت (NX-API، یا Cisco Nexus با SNMP — بخش ۱۳):** یک policer روی پورت:

```
policy-map type qos PANEL-RL-100M
  class class-default
    police cir 100 mbps bc 200 ms conform transmit violate drop
interface Ethernet1/5
  service-policy type qos input PANEL-RL-100M
  service-policy type qos output PANEL-RL-100M
```

- ورودی پورت آپلود سرور است و خروجی دانلودش. برخی مدل‌ها و نسخه‌های نکسوس policer خروجی را نمی‌پذیرند؛ آن وقت
  فقط ورودی محدود می‌شود و نتیجه همین را می‌گوید.
- policy-map برای هر سرعت یکی است و بین پورت‌ها مشترک. پنل فقط policyهایی را که با `PANEL-RL-` شروع می‌شوند عوض
  یا برمی‌دارد. اگر روی پورت policy دیگری باشد، **دست نمی‌خورد** و فرمان رد می‌شود.
- پورت محافظت‌شده محدودیت نمی‌گیرد. برای پورت وصل به سرور، نام پورت باید تایپ شود.
- سقف صفر یعنی برداشتن محدودیت. پس از هر فرمان، وضعیت واقعی از `show running-config interface` خوانده می‌شود.

## ۱۱. پشتیبان پیکربندی (NX-API، یا سیسکو با SNMP — بخش ۱۳)

هر `switch_backup_hours` ساعت (پیش‌فرض ۲۴، در **تنظیمات ← پایش**؛ صفر یعنی خاموش) و پس از هر فرمان موفق پنل،
`show running-config` خوانده می‌شود. خط‌های زمان‌دار (`!Time:` و…) کنار گذاشته می‌شوند و نسخه **فقط وقتی با قبلی
فرق دارد** ذخیره می‌شود؛ زمان آخرین بررسی همیشه ثبت می‌شود. «پشتیبان‌گیری همین حالا» هم هست.

سربرگ **پشتیبان پیکربندی** در صفحه سوییچ: فهرست نسخه‌ها (خودکار، دستی، پس از فرمان — با نام درخواست‌دهنده)،
تفاوت هر نسخه با قبلی، متن کامل و دانلود.

**رازها:** پیکربندی هش گذرواژه کاربران، کامیونیتی SNMP و کلید TACACS/RADIUS را دارد. فقط حساب مدیر آن را می‌بیند،
و پیش‌فرض رازها با `••••••` پوشیده‌اند — در متن، در تفاوت دو نسخه، و در فایل دانلودی. تیک «نمایش رازها» آن‌ها را
نشان می‌دهد. نسخه کامل در دیتابیس است؛ از پشتیبان دیتابیس هم مثل خود سوییچ محافظت کنید.

## ۱۲. گزارش پورت‌ها و صدک ۹۵

**سوییچ‌ها ← گزارش پورت‌ها**: برای ماه جاری، ماه قبل یا بازه دلخواه، و همه سوییچ‌ها یا یکی:

| ستون | چیست |
|---|---|
| حجم | ورودی و خروجی از تجمیع روزانه |
| صدک ۹۵ | از نمونه‌های پنج‌دقیقه‌ای (حجم × ۸ ÷ ۳۰۰)، روی بزرگ‌ترِ ورودی و خروجی هر بازه — همان روشی که دیتاسنترها پهنای باند را فاکتور می‌کنند. ورودی و خروجی جدا هم نشان داده می‌شوند |
| اوج | بیشترین سرعت روزانه |
| میانگین بهره‌وری | حجم بزرگ‌ترِ دو جهت نسبت به ظرفیت پورت در طول بازه |
| خطا، قطع | مجموع خطا و تعداد قطع (یا قطع و وصل کوتاه) |

با کلیک روی سرآیند ستون مرتب می‌شود؛ خروجی CSV برای اکسل. صدک ۹۵ فقط از روزهایی است که تجمیع پنج‌دقیقه‌ای دارند
(از نصب این نسخه به بعد، و تا `switch_5min_days` روز).

در داشبورد، کارت سوییچ‌ها وضعیت هر سوییچ و پرمصرف‌ترین پورت‌ها نسبت به ظرفیت را نشان می‌دهد.

## ۱۳. محدودیت سرعت و پشتیبان پیکربندی با SNMP v3 (Cisco Nexus)

SNMP راه استانداردی برای تنظیم QoS یا خواندن running-config ندارد. سیسکو یک راه دارد: **CISCO-CONFIG-COPY-MIB**.
پنل با SNMP SET (در v3 رمزنگاری‌شده) به سوییچ می‌گوید:

- **محدودیت سرعت:** یک تکه پیکربندی (همان policy-map و service-policy بخش ۱۰) را از سرور پنل بردار و در
  running-config ادغام کن.
- **پشتیبان:** running-config را برای سرور پنل بفرست.

پس **جهت اتصال برعکس است: سوییچ به سرور پنل وصل می‌شود.** و این MIB پورت ندارد؛ سوییچ همیشه به پورت استاندارد می‌رود:

| روش | پورت روی سرور پنل | |
|---|---|---|
| **SFTP** (پیشنهادی) | TCP ۲۲ — sshd خود سرور، با کاربر محدود | رمزنگاری‌شده. نام کاربری و گذرواژه با SNMP v3 رمزشده به سوییچ داده می‌شود |
| **TFTP** | UDP ۶۹ — سرور کوچک داخل ورکر | بی‌رمز: پیکربندی، با هش گذرواژه‌ها و کامیونیتی‌ها، روی شبکه مدیریت باز می‌رود |

### هر کار چطور انجام می‌شود

محدودیت سرعت روی پورت `Ethernet1/5`:

۱. running-config خوانده می‌شود (سوییچ می‌فرستد). اگر روی پورت policy دیگری باشد که پنل نگذاشته، کار همین‌جا متوقف
   می‌شود و چیزی عوض نمی‌شود.
۲. تکه پیکربندی ساخته و با نام تصادفی یک‌بارمصرف در دسترس سوییچ گذاشته می‌شود؛ سوییچ برمی‌دارد و ادغام می‌کند.
۳. running-config دوباره خوانده می‌شود و نتیجه **از روی آن** گزارش می‌شود. «کپی موفق» یعنی فایل رسید، نه اینکه هر
   خطش پذیرفته شد — اگر سوییچ policer خروجی را نپذیرد، نتیجه می‌گوید فقط ورودی محدود شد.
۴. فایل‌ها پاک می‌شوند. پس از هر فرمان موفق، همان پیکربندی تازه به‌عنوان نسخه «پس از فرمان» ذخیره می‌شود.

هر خواندن running-config چند ثانیه طول می‌کشد؛ هر فرمان محدودیت با SNMP حدود ۱۰ تا ۳۰ ثانیه است.

### ۱) روی سوییچ: کاربر SNMP v3 با اجازه نوشتن

```
configure terminal
  snmp-server user panelrw network-admin auth sha <گذرواژه-احراز> priv aes-128 <گذرواژه-رمز>
end
show snmp user
```

نقش `network-admin` لازم است: کپی در running-config یعنی تغییر پیکربندی. دسترسی SNMP را با ACL فقط به آی‌پی سرور
پنل محدود کنید.

### ۲) روی سرور پنل: کاربر SFTP

```bash
cd /root/pasargad-monitor
sudo bash scripts/setup-switch-sftp.sh
```

اسکریپت کاربر `switchxfer` را می‌سازد که:
- فقط SFTP دارد — شل، تونل و فوروارد ندارد (`ForceCommand internal-sftp`)
- در `/srv/pasargad-sftp` زندانی است (`ChrootDirectory`) و فقط در زیرپوشه `files` می‌نویسد
- گذرواژه تصادفی ۲۴ نویسه‌ای دارد که در پایان چاپ می‌شود

پیکربندی sshd پیش از reload با `sshd -t` سنجیده می‌شود و اگر خطا داشت نسخه قبلی برمی‌گردد. اجرای دوباره بی‌خطر است
و گذرواژه تازه می‌سازد.

### ۳) docker-compose و .env

```
# .env
SWITCH_SFTP_DIR=/srv/pasargad-sftp/files
# فقط اگر TFTP لازم است: آی‌پی‌ای از سرور که سوییچ‌ها به آن می‌رسند
# SWITCH_TFTP_BIND=10.0.0.10
```

```bash
docker compose up -d worker
```

پوشه `SWITCH_SFTP_DIR` به ورکر وصل می‌شود (`/transfer`). پورت ۶۹ TFTP پیش‌فرض فقط روی `127.0.0.1` منتشر می‌شود —
یعنی از بیرون بسته است — تا وقتی `SWITCH_TFTP_BIND` را بدهید. ورکر هم فقط وقتی کاری در جریان است روی آن گوش می‌دهد.

### ۴) در پنل

- **تنظیمات ← پایش ← انتقال پیکربندی سوییچ با SNMP:** آی‌پی سرور پنل از دید سوییچ‌ها، کاربر و گذرواژه SFTP، و مسیر
  `/files`. فقط حساب مدیر این‌ها را عوض می‌کند: هر کس نشانی را عوض کند، پشتیبان بعدی به سرور او می‌رود.
- **ویرایش سوییچ:** «انتقال فایل پیکربندی» را SFTP (یا TFTP) بگذارید، و «اجازه نوشتن» v3 روشن باشد.

پس از خواندن بعدی سوییچ (که سیسکو و NX-OS بودنش را از sysDescr تشخیص می‌دهد)، دکمه «تنظیم محدودیت» و سربرگ
«پشتیبان پیکربندی» فعال می‌شوند. اول **پشتیبان‌گیری همین حالا** را بزنید: اگر موفق شد، مسیر سوییچ تا پنل درست است.

### نکته‌ها

- **مسیر شبکه:** سوییچ باید از شبکه‌ای که کپی را انجام می‌دهد به آی‌پی سرور پنل برسد. روی نکسوس اگر سرور پنل
  فقط از راه mgmt0 در دسترس است، مسیر VRF مدیریت را بررسی کنید؛ خطای «تایم‌اوت» یعنی همین.
- **کلید میزبان SFTP:** اگر سوییچ برای پذیرش کلید میزبان سرور پنل سوال کند، یک بار دستی از خود سوییچ امتحان کنید:
  `copy running-config sftp://switchxfer@<آی‌پی-پنل>/files/test.cfg vrf management` و کلید را بپذیرید؛ بعد
  فایل test.cfg را از `/srv/pasargad-sftp/files` پاک کنید.
- **IOS / Catalyst:** پشتیبان پیکربندی با همین روش کار می‌کند؛ محدودیت سرعت نه، چون نحو QoS آن فرق دارد.
- **برندهای دیگر:** این MIB مال سیسکوست؛ میکروتیک، هوآوی و جونیپر راه دیگری دارند و پشتیبانی نمی‌شوند.

### اگر عددی درست نیست

تجزیه‌گر با نمونه‌های خروجی NX-OS 9.3 آزموده شده (`python3 scripts/test-switch.py`). نام فیلدهای جیسون بین
نسخه‌ها گاهی فرق دارد. برای مقایسه، روی سوییچ:

```
show interface ethernet1/1 | json
show system resources | json
show environment power | json
```

و خروجی را با آنچه پنل نشان می‌دهد مقایسه کنید.
