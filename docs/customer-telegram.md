# تلگرام مشتری

مشتری تلگرامش را به حسابش وصل می‌کند و هشدارها را آنجا هم می‌گیرد.

| رویداد | تلگرام | ایمیل | پیامک |
|---|---|---|---|
| ۹۰٪ سهمیه ترافیک | ✓ | ✓ | ✓ |
| اتمام سهمیه | ✓ | ✓ | ✓ |
| موعد تمدید | ✓ | ✓ | ✓ |
| پرداخت فاکتور | ✓ | ✓ | ✓ |
| پاسخ تیکت | ✓ | ✓ | — |

پاسخ تیکت عمداً پیامک ندارد: فوری نیست و هزینه‌اش روی هر رفت‌وبرگشت
گفتگو جمع می‌شود.

## اتصال

```
پرتال ← پروفایل ← «اتصال تلگرام»
   ↓
کد یکبارمصرف ساخته می‌شود، لینک t.me/<ربات>?start=<کد>
   ↓
مشتری در تلگرام Start را می‌زند
   ↓
ورکر پیام را می‌خواند، شناسه گفتگو را از خودِ پیام برمی‌دارد
   ↓
حساب وصل شد؛ صفحه پروفایل خودش به‌روز می‌شود
```

### شناسه گفتگو از تلگرام می‌آید، نه از مرورگر

**این کل نکته امنیتی این بخش است.** اگر مشتری شناسه را در یک فرم
می‌نوشت، هر کسی می‌توانست شناسه یک نفر دیگر را بنویسد و هشدارهای او را
بگیرد.

مسیر `/api/portal/telegram` فقط یک کد می‌سازد. شناسه را ورکر از خود
پیامی که به ربات رسیده برمی‌دارد.

### کد اتصال

پنج دقیقه اعتبار، یکبارمصرف، و ساخته‌شده با `randomBytes`. مصرفش در
**همان به‌روزرسانی‌ای** انجام می‌شود که شرط‌ها را بررسی می‌کند، وگرنه دو
پیام همزمان یک کد را دو بار مصرف می‌کنند.

### یک گفتگو، یک حساب

ایندکس یکتا روی `customers.telegram_chat_id`. اگر گفتگویی از قبل به
حساب دیگری وصل بوده، آن اتصال پیش از اتصال تازه پاک می‌شود — وگرنه
ایندکس یکتا به‌روزرسانی را رد می‌کند و کاربر فقط یک خطای نامفهوم
می‌گیرد.

## چرا خواندن پیام، نه وب‌هوک

وب‌هوک یک مسیر عمومی تازه می‌خواهد و یک قدم راه‌اندازی (`setWebhook`) که
فراموش‌شدنش هیچ خطایی نمی‌سازد: اتصال‌ها فقط بی‌صدا کار نمی‌کنند — بدترین
شکل خرابی.

ورکر از قبل همیشه در حال اجراست و برای فرستادن پیام هم به تلگرام وصل
می‌شود. `getUpdates` هیچ راه‌اندازی تازه‌ای نمی‌خواهد.

**اگر روی این ربات وب‌هوک تنظیم کرده باشید، اتصال کار نمی‌کند.** ورکر
این را صریح در لاگ می‌گوید:

```bash
docker compose logs worker | grep تلگرام
```

برای برداشتنش:

```bash
curl -s "https://api.telegram.org/bot<توکن>/deleteWebhook"
```

### offset

`getUpdates` هر پیام را تا وقتی تأیید نشده دوباره می‌دهد. `offset` در
`settings.telegram_updates_offset` نگه داشته می‌شود، وگرنه ورکر پس از هر
ری‌استارت همان `/start` قدیمی را دوباره پردازش می‌کند.

**offset همیشه جلو می‌رود، حتی اگر پردازش پیامی شکست خورده باشد.** اگر
پشت شرط موفقیت می‌رفت، یک پیام خرابِ همیشگی ورکر را در جای خودش قفل
می‌کرد و هیچ اتصال تازه‌ای انجام نمی‌شد.

## یک نقطه برای همه کانال‌ها

`lib/customer-notify.ts` تابع `notifyCustomer` را دارد: پیامک، ایمیل و
تلگرام، هر سه مستقل و هیچ‌کدام جلوی دیگری را نمی‌گیرد.

پیش از این، هر جا که به مشتری خبر می‌داد خودش پیامک و ایمیل را جدا صدا
می‌زد. یعنی افزودن تلگرام باید در هر کدام تکرار می‌شد، و آن یکی که
فراموش می‌شد هیچ خطایی نمی‌داد — فقط مشتری خبردار نمی‌شد.

`worker/customer-alerts.mjs` نسخه دوقلوی همین منطق را دارد. تکرار عمدی
است: ورکر هشدار نباید به بالا بودن اپ وب وابسته باشد. **اگر یکی را عوض
کردید، دیگری را هم عوض کنید.**

### اتصال مرده خودش پاک می‌شود

اگر مشتری ربات را بلاک کند یا گفتگو را پاک کند، تلگرام خطای
`blocked` یا `chat not found` می‌دهد. آن شناسه همان‌جا پاک می‌شود.

بدون این، هر بار دوباره تلاش می‌شد و هر بار همان خطا — و مشتری در پرتال
«متصل» می‌دید در حالی که هیچ پیامی نمی‌گرفت.

## دستورهای ربات

| فرمان | کار |
|---|---|
| `/start <کد>` | اتصال حساب |
| `/start` | راهنمای کوتاه |
| `/stop` | قطع اتصال |

هر پیام دیگری یک راهنمای کوتاه می‌گیرد. سکوت، کاربر را سردرگم می‌کند.

## راه‌اندازی

۱. `TELEGRAM_BOT_TOKEN` در `.env` (همان توکنی که برای هشدار ادمین
استفاده می‌شود).

۲. مهاجرت:

```bash
docker compose exec -T postgres psql -U pasargad -d pasargad_monitor < db/migrations/043_customer_telegram.sql
```

۳. ورکر که بالا آمد، خودش با `getMe` نام ربات را می‌گیرد و در تنظیمات
می‌نویسد. تا وقتی این نام خالی است، مشتری نمی‌تواند وصل شود و صفحه
تنظیمات هشدار می‌دهد.

**دسترسی به `api.telegram.org` از ایران:** با `TELEGRAM_API_BASE` از یک
واسط عبور دهید — همان متغیری که برای فرستادن هشدار هم استفاده می‌شود.
راهنمای قدم‌به‌قدم راه‌اندازی واسط روی سرور خارج:
[docs/telegram-relay.md](telegram-relay.md)
